# 请求代码审查

在请求外部审查之前，通过结构化的自审确保代码质量。

## 预审查清单

请求审查前，验证：

- [ ] 所有测试通过
- [ ] 无 lint 错误或警告
- [ ] 代码遵循现有模式和约定
- [ ] 无未跟踪的 TODO/FIXME
- [ ] 错误处理完整
- [ ] 边界情况已覆盖
- [ ] 无不必要的复杂度（YAGNI）
- [ ] 无重复代码（DRY）
- [ ] 注释解释"为什么"，而非"是什么"
- [ ] 规格需求已满足

## 审查请求格式

请求审查时，提供：

```markdown
## 代码审查请求

**变更：** <变更名称>
**规格：** `openspec/changes/<变更名称>/specs/`
**设计：** `docs/designs/YYYY-MM-DD-<主题>-design.md`
**计划：** `docs/plans/YYYY-MM-DD-<主题>-plan.md`

### 变更内容
- 变更的简要摘要

### 审查重点
- 特别关注的领域
- 需要验证的决策

### 验证
- 测试结果：X 通过，0 失败
- 覆盖率：X%
```

## 严重级别

审查或接收反馈时：

- **严重**：阻塞合并。逻辑错误、安全问题、数据丢失风险。
- **重要**：应该修复。性能问题、错误处理差、缺少测试。
- **次要**：最好修复。命名、风格、小改进。
- **建议**：可选。个人偏好、琐碎的风格选择。

## 规则

- 绝不跳过预审查清单
- 在审查请求中始终引用规格和设计
- 在继续前解决严重和重要问题
- 记录决策供将来参考
