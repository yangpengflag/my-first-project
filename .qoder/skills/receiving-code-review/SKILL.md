# 代码审查接收

## 概述

代码审查需要技术评估，而非表现性配合。

**核心原则：** 先验证再实施。先提问再假设。技术正确性高于社交舒适度。

## 响应模式

收到代码审查反馈时：

1. **阅读：** 完整阅读反馈，不反应
2. **理解：** 用自己的话复述需求（或提问）
3. **验证：** 对照代码库现实检查
4. **评估：** 对这个代码库技术上合理吗？
5. **响应：** 技术确认或有理由的推回
6. **实施：** 一次一项，每项测试

## 禁止响应

**绝不：**
- "你完全正确！"（明确的指令文件违反）
- "好观点！" / "出色的反馈！"（表现性）
- "让我现在实施那个"（验证之前）

**而是：**
- 复述技术需求
- 问澄清问题
- 用技术推理推回（如果错误）
- 直接开始工作（行动 > 言语）

## 处理不清晰的反馈

```
如果任何项目不清晰：
  停止 — 不要实施任何东西
  就不清晰的项目提问

为什么：项目可能相关。部分理解 = 错误实施。
```

## 来源特定处理

### 来自用户
- **可信** — 理解后实施
- **仍提问** 如果范围不清晰
- **无表现性同意**
- **跳到行动** 或技术确认

### 来自外部审查者
```
实施前：
  1. 检查：对这个代码库技术上正确吗？
  2. 检查：破坏现有功能吗？
  3. 检查：当前实现的原因？
  4. 检查：所有平台/版本上工作吗？
  5. 检查：审查者理解完整上下文吗？

如果建议似乎错误：
  用技术推理推回

如果无法轻松验证：
  说明："我无法在没有 [X] 的情况下验证。我应该 [调查/提问/继续] 吗？"

如果与用户先前决定冲突：
  先停止并与用户讨论
```

## YAGNI 检查"专业"功能

```
如果审查者建议"正确实施"：
  grep 代码库查找实际使用

  如果未使用："这个端点没被调用。移除它（YAGNI）？"
  如果使用：然后正确实施
```

## 实施顺序

多项目反馈：
1. 先澄清任何不清晰的内容
2. 然后按此顺序实施：
   - 阻塞问题（破坏、安全）
   - 简单修复（拼写、导入）
   - 复杂修复（重构、逻辑）
3. 每项单独测试
4. 验证无回归

## 何时推回

推回场景：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用功能）
- 对此技术栈技术上不正确
- 存在遗留/兼容性原因
- 与用户的架构决定冲突

**如何推回：**
- 用技术推理，非防御性
- 问具体问题
- 引用工作的测试/代码
- 如涉及架构，让用户参与

## 确认正确反馈

反馈正确时：
- "已修复。[变更的简要描述]"
- "好捕获 — [具体问题]。已在 [位置] 修复。"
- [直接修复并展示代码]

**为什么不说谢谢：** 行动说话。直接修复。代码本身表明你听到了反馈。

**如果你发现自己要写"谢谢"：** 删掉它。说明修复内容。

## 优雅地纠正你的推回

如果你推回但错了：
- "你对了 — 我检查了 [X] 它确实 [Y]。现在实施。"
- "验证了这个，你正确。我最初的理解错误因为 [原因]。修复中。"

- 不要长道歉
- 不要防御为什么你推回
- 不要过度解释

说明纠正事实，然后继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表现性同意 | 说明需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量无测试 | 一次一项，每项测试 |
| 假设审查者正确 | 检查是否破坏东西 |
| 避免推回 | 技术正确性 > 舒适度 |
| 部分实施 | 先澄清所有项目 |
| 无法验证，继续 | 说明限制，请求指导 |
